# HTTP Gateway: Единый входной шлюз системы

Репозиторий [**`gateway-service`**](https://github.com/orbit-polytech/gateway-service) представляет собой единственный компонент бэкенда, который принимает внешние запросы от клиентов (мобильного приложения `mobile`, Telegram-бота `bot-service` и веб-браузеров). 

Внутренние микросервисы не имеют публичных HTTP-портов и не видны из интернета.

---

## 1. Задачи и зона ответственности Gateway

Шлюз выполняет строго инфраструктурные и транспортные задачи:
* **Аутентификация**: проверка валидности входящего JWT (по открытому ключу Ed25519) и извлечение `user_id` и `role`.
* **Санитизация заголовков**: принудительное удаление любых служебных заголовков `x-user-*` и `x-internal-*`, присланных снаружи.
* **Ограничение частоты (Rate Limiting)**: защита сервисов от DDoS и спам-запросов (по IP и по авторизованному пользователю).
* **Трансляция протоколов**: приём REST/JSON HTTP-запросов, вызов внутренних микросервисов по бинарному gRPC и возврат ответа клиенту в формате JSON.
* **CORS**: настройка разрешённых заголовков и origins для веб-клиентов.

> [!IMPORTANT]
> **В Gateway нет бизнес-логики.** Gateway не проверяет, принадлежит ли задача студенту, не рассчитывает дедлайны и не ходит в базу данных напрямую. Если в коде Gateway появляется вызов базы данных — это архитектурная ошибка.

## 3. Границы доверия и передача `x-user-id`

Согласно принятому в проекте архитектурному решению **ADR-004**:
1. Клиент присылает HTTP-запрос с заголовком `Authorization: Bearer <JWT>`.
2. Gateway проверяет подпись токена с помощью публичного ключа `jwt_ed25519.pub`.
3. Gateway **вырезает** любые потенциально опасные заголовки `x-user-*`, чтобы злоумышленник не мог передать чужой идентификатор.
4. Gateway упаковывает проверенный `sub` (UUID студента) в gRPC-метаданные `x-user-id` и вызывает внутренний сервис.
5. Микросервисы доверяют этому заголовку, поскольку их порты закрыты от прямого доступа извне.
