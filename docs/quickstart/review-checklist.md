# Чек-лист код-ревью и стандарты чистого кода

Код-ревью в Orbit AI — это не экзамен и не поиск опечаток (опечатки и форматирование находит линтер). Это совместное обсуждение архитектурных решений, безопасности и читаемости кода.

---

## 1. Общие стандарты чистого кода (для всех языков)

* **Говорящие имена**: переменная объясняет своё назначение. `deadline`, а не `d`; `activeTasks`, а не `list2`.
* **Принцип единственной ответственности (SRP)**: функция делает ровно одну вещь. Если в описании функции вслух звучит союз «и» («загрузить задачу из базы **и** отправить push»), её нужно разделить.
* **Ранний выход (Guard Clauses)**: избегайте глубокой вложенности `if-else`. Сначала проверяем условия ошибок и выходим, а основной сценарий пишем без лишнего отступа:

```go
// ПЛОХО: глубокая лесенка вложенности
func (t *Task) Complete(now time.Time) error {
    if t.status != StatusDeleted {
        if t.status != StatusDone {
            t.status = StatusDone
            t.completedAt = now
            return nil
        } else {
            return ErrInvalidTransition
        }
    } else {
        return ErrInvalidTransition
    }
}

// ХОРОШО: плоский код с ранним выходом
func (t *Task) Complete(now time.Time) error {
    if t.status != StatusOpen {
        return ErrInvalidTransition
    }
    t.status = StatusDone
    t.completedAt = now
    return nil
}
```

* **Осмысленные комментарии**: пишите в комментариях *почему* сделано так, а не *что* делает код. Код и так показывает, что он делает.
* **Никакого закомментированного кода**: мёртвый закомментированный код удаляется без жалости. При необходимости его всегда можно найти в истории Git.
* **Правило трёх повторов**: не копируйте один и тот же блок кода в третий раз. На третий раз вынесите логику в отдельную функцию или хелпер рядом.
* **Именованные константы**: никаких «магических чисел». Пишите `maxTitleLength = 200` вместо числа `200` посреди валидации.
* **Нулевая терпимость к секретам**: токены, пароли, приватные ключи и `initData` никогда не пишутся в коде или тестах.

## 2. Специфика по языкам проекта

### Go (Golang)
* Автоматическое форматирование строго через `gofumpt` и `goimports`. Конфиг линтера задан в `.golangci.yml`.
* Ошибки проверяются сразу же после вызова. Игнорирование ошибки (`_ = fn()`) допустимо только с явным комментарием, объясняющим, почему сбой безопасен.
* Ошибки оборачиваются через `fmt.Errorf("...: %w", err)` и сравниваются через `errors.Is` / `errors.As`.
* Все методы структуры используют один вид ресивера: либо только указатели `(t *Task)`, либо только значения `(t Task)`.
* Каждая запускаемая горутина обязана иметь способ остановки (через `ctx.Done()` или канал завершения). Бесконечные горутины без контроля жизненного цикла — это критическая утечка памяти.
* Вызов `defer rows.Close()` ставится сразу после успешного запроса к базе данных, а после цикла `for rows.Next()` обязательна проверка `rows.Err()`.
* Конструкторы возвращают конкретные структуры (`*TaskRepository`), а не интерфейсы (`TaskRepo`). Интерфейсы объявляются на стороне потребителя (consumer-driven interfaces).

### Python (AI & Bot)
* Следование стандартам PEP 8, линтер и форматтер — `ruff` (`ruff check`, `ruff format`).
* Строгая статическая типизация для всех функций и методов (`mypy --strict`).
* В асинхронном коде (`async def`) категорически запрещены блокирующие вызовы (`requests`, `time.sleep`). Используются `httpx.AsyncClient` и `asyncio.sleep`.
* Запрещены пустые перехваты `except:` или `except Exception: pass`. Ошибки логируются с контекстом или пробрасываются дальше.
* Для сущностей данных используются `dataclass(frozen=True)` или модели Pydantic, а не нетипизированные словари (`dict`).

### Dart & Flutter (Mobile)
* Соблюдение Effective Dart, линтер `flutter_lints`, форматирование `dart format`.
* Использование `const`-конструкторов везде, где свойства виджета неизменяемы, для оптимизации перерисовки дерева Flutter.
* Метод `build()` виджета не должен содержать побочных эффектов: никаких сетевых запросов, мутаций состояния или вызовов навигатора.
* Большие методы `build()` декомпозируются на отдельные классы виджетов, а не на локальные методы-функции.
* Бизнес-логика живет во ViewModel, виджет только отображает состояние и передает пользовательские события.
* Запрещено обращение к `BuildContext` после асинхронного `await` без проверки `if (!context.mounted) return;`.

## 3. Почему запрещены пакеты-свалки (`util`, `common`, `helpers`)

В Go создание общих пакетов `util`, `common`, `helpers` или `misc` — грубая ошибка (антипаттерн «ящик со всяким хламом»). Они размывают ответственность и со временем вызывают циклические импорты (`import cycle not allowed`).

Вместо одного общего мешка код раскладывается по двум понятным правилам:

### 1. Узкие пакеты с говорящими именами
Каждый вспомогательный пакет решает **ровно одну конкретную задачу**:

| Антипаттерн (пакет-свалка) | Хорошо (чёткий фокус) | Пример вызова в коде Go |
|---|---|---|
| `util.NewUUID()` | Пакет `idgen` | `idgen.NewTaskID()` |
| `helpers.HashPassword()` | Пакет `hasher` или `crypto` | `hasher.Hash(password)` |
| `common.ValidateEmail()` | Пакет `validator` | `validator.IsEmail(str)` |
| `utils.Now()` | Пакет `clock` | `clock.Now()` |

### 2. Размещение логики по месту использования
Если вспомогательная функция нужна только в одном месте (например, расчёт дедлайна в задачах), ей вообще не место в публичных пакетах — положите её прямо в `internal/domain/task.go`.

## 4. Чек-лист проверки Pull Request

Скопируйте этот чеклист в комментарий к PR при проведении ревью:

```markdown
### Архитектура и слои
- [ ] Файлы расположены строго в своих слоях (domain не импортирует БД и gRPC, transport не содержит бизнес-логики)
- [ ] Отсутствуют пакеты-свалки `util`, `common`, `helpers` (код разделен на узкие пакеты `idgen`, `hasher` и т.д.)
- [ ] Новые переменные окружения описаны в `config` и добавлены в `.env.example`

### Логика и надежность
- [ ] Код полностью решает поставленную в задаче цель
- [ ] Ошибки корректно обрабатываются и возвращаются, а не подавляются
- [ ] Изменения защищены от состояний гонки (оптимистичная блокировка, транзакции, уникальные индексы)
- [ ] Повторный вызов с одинаковым `Idempotency-Key` не создаёт дубликат записи (AIP-155)

### Безопасность
- [ ] Проверено владение ресурсом: студент не может просмотреть или изменить чужие задачи/оценки (защита от IDOR)
- [ ] Роли, баланс, права и суммы никогда не принимаются из тела запроса клиента
- [ ] В логах отсутствуют токены, пароли, смс-коды и Telegram `initData`
- [ ] Все SQL-запросы параметризованы (исключены SQL-инъекции)
- [ ] Публичные эндпоинты защищены ограничением частоты запросов (Rate Limiting)

### Тестирование
- [ ] Написаны тесты на успешный путь (Happy Path) и граничные случаи (ошибки, пустые значения)
- [ ] Тесты детерминированы: не зависят от системного времени (используется mock Clock) и порядка запуска
- [ ] Все тесты компилируются и проходят на 100%

### Читаемость
- [ ] Назначение функций и переменных понятно с первого взгляда без автора рядом
- [ ] Удален весь закомментированный код и отладочные `println`/`print`
```
