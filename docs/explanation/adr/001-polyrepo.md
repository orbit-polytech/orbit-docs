# ADR-001: Выбор Polyrepo вместо Monorepo

## Статус
**Принято (Accepted)** — Октябрь 2026 г.

---

## Контекст
В проекте Orbit AI участвует команда из 10 разработчиков с различным уровнем опыта (Go бэкенд, Python AI/боты, Flutter мобайл). Первоначальное рассмотрение монорепозитория или использования Git Submodules (как в предыдущих экспериментах команды) выявило следующие критические проблемы:

1. **Конфликты слияния и блокировки:** При 10 разработчиках в одном репозитории коммиты в инфраструктуру или CI постоянно блокируют работу мобильных разработчиков и бэкендеров.
2. **Проблемы с Git Submodules:** Механизм субмодулей крайне сложен для новичков (часто возникают состояния `detached HEAD`, забытые команды `git submodule update --init`, рассинхронизация коммитов).
3. **Разграничение прав доступа и CI/CD:** В монорепозитории сложно настроить изолированные триггеры GitHub Actions на каждый сервис без сложного скриптования путей (path filtering).
4. **Релизы и независимое версионирование:** Каждый микросервис должен иметь собственный жизненный цикл релизов и возможность публикации Docker-образов в GHCR независимо от остальных.

---

## Решение
Принято решение организовать проект по модели **Polyrepo (Организация микросервисных репозиториев на GitHub)**:

1. Создана официальная организация GitHub: [`orbit-polytech`](https://github.com/orbit-polytech).
2. Под каждый логический сервис выделен отдельный репозиторий:
   - `contracts` — единственный репозиторий Protobuf-схем и сгенерированного кода;
   - `orbit-service-template` — эталонный шаблон микросервиса на Go;
   - `gateway-service` — API Gateway (REST $\leftrightarrow$ gRPC);
   - `tasks-service`, `schedule-service`, `navigation-service`, `auth-service`, `users-service`, `notification-service` — Go бэкенды;
   - `ai-service`, `bot-service` — Python сервисы;
   - `client-mobile` — мобильное приложение на Flutter;
   - `infra` — единый репозиторий локальной оркестрации (Docker Compose, скрипты баз данных, Prometheus, Grafana);
   - `orbit-docs` — сайт технической документации.

---

## Последствия

### Позитивные последствия:
- **Полная изоляция кодовой базы:** Разработчик Flutter работает только в `client-mobile`, не трогая код бэкенда на Go.
- **Чистый и быстрый CI/CD:** Каждый репозиторий имеет легковесный workflow (20–40 секунд на проверку линтеров и тестов).
- **Независимые релизы:** Баг-фикс в `schedule-service` деплоится без пересборки остальных 7 сервисов.
- **Отсутствие проблем с Git Submodules:** Контракты подключаются через стандартные пакетные менеджеры (`go get`, `pip install`).

### Негативные последствия и компромиссы:
- **Необходимость координации контрактов:** Изменение API требует предварительного PR в `contracts` и последующего обновления версий в зависимых сервисах.
- **Оркестрация локального запуска:** Для запуска полного контура требуется склонировать `infra` и запускать сервисы в Docker.
