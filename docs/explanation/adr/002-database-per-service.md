# ADR-002: Раздельные БД для каждого сервиса (Database-per-Service)

## Статус
**Принято (Accepted)** — Октябрь 2026 г.

---

## Контекст
В микросервисной архитектуре распространен антипаттерн «Общая база данных» (Shared Database), когда несколько сервисов напрямую читают и пишут в одни и те же таблицы PostgreSQL через единый пул соединений.

В проекте Orbit AI это приводило бы к следующим рискам:
1. **Тесная связанность схем данных (Tight Coupling):** Изменение колонки в таблице пользователей в одном сервисе ломает SQL-запросы в других сервисах без явного предупреждения.
2. **Нарушение инвариантов бизнес-логики:** Любой сервис мог бы изменить статус задачи или пароль в обход валидаций доменного слоя.
3. **Конкуренция за ресурсы БД (Deadlocks):** Тяжелые аналитические запросы сервиса расписания или векторного поиска RAG блокировали бы транзакции создания задач.
4. **Невозможность раздельного масштабирования:** База данных становилась бы единой точкой отказа (Single Point of Failure).

---

## Решение
Принят классический архитектурный паттерн **Database-per-Service (База данных на микросервис)**:

1. Каждый сервис владеет **собственной изолированной базой данных**:
   - `tasks-service` $\rightarrow$ `tasks_db`;
   - `schedule-service` $\rightarrow$ `schedule_db`;
   - `auth-service` $\rightarrow$ `auth_db`;
   - `ai-service` $\rightarrow$ `ai_knowledge_db` (с расширением `pgvector`).
2. В локальном окружении `infra` сервисы могут использовать один инстанс PostgreSQL кластера, но **строго под разными именами баз данных и пользователями**.
3. **Прямые SQL-соединения между сервисами категорически запрещены:** Ни один сервис не имеет права подключаться к чужой базе данных.
4. Любой обмен данными между сервисами происходит **исключительно через gRPC API** или **асинхронные события RabbitMQ**.
5. Запрещены внешние ключи (Foreign Keys) на уровне СУБД между таблицами разных контекстов. Связь осуществляется через логические строковые идентификаторы (например, `owner_id VARCHAR(64)`).

---

## Последствия

### Позитивные последствия:
- **Полная независимость миграций:** Миграции `tasks_db` через Goose выполняются без оглядки на расписание или авторизацию.
- **Изоляция сбоев:** Падение или перегрузка БД расписания не влияет на работоспособность сервиса задач.
- **Оптимизация под стек:** `ai-service` подключает тяжелое расширение `vector`, не загрязняя остальные базы данных.

### Негативные последствия и компромиссы:
- **Невозможность выполнения распределенных JOIN-запросов:** Объединение данных происходит на уровне приложения (в Gateway) или через репликацию событий.
- **Повышенное потребление соединений:** Каждому сервису выделяется собственный пул соединений (`pgxpool`).
