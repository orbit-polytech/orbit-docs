# ADR-003: RabbitMQ для асинхронных событий

## Статус
**Принято (Accepted)** — Октябрь 2026 г.

---

## Контекст
В системе Orbit AI возникают ситуации, когда действие в одном сервисе требует реакции одного или нескольких других сервисов без жесткой временной синхронизации:
- При создании дедлайна по задаче в `tasks-service` необходимо отправить Push-уведомление через `notification-service`.
- При изменении расписания в `schedule-service` необходимо обновить векторный индекс в `ai-service` и уведомить старосту в Telegram через `bot-service`.

Если делать синхронные вызовы по gRPC в цепочке ($A \rightarrow B \rightarrow C$), то:
1. Запрос пользователя блокируется на суммарное время выполнения всех шагов.
2. Падение сервиса уведомлений приводит к отказу создания задачи у студента.
3. Добавление нового подписчика требует изменения кода сервиса-источника.

---

## Решение
В качестве единого шинного брокера асинхронных событий выбран **RabbitMQ (AMQP 0-9-1)**:

1. **Модель Publish/Subscribe:**
   - Сервисы-издатели отправляют сообщения в Topic Exchanges (например, `tasks.events`, `schedule.events`).
   - Сервисы-подписчики декларируют собственные независимые очереди с нужными routing keys (например, очередь `notification.task_events` слушает `task.*`).
2. **Гарантия доставки через Transactional Outbox:**
   - Публикация событий защищается сохранением в таблицу `outbox_events` в одной транзакции с бизнес-данными (исключение Dual-Write).
3. **Персистентность и подтверждения:**
   - Сообщения публикуются с флагом `DeliveryMode = 2` (Persistent).
   - Потребители используют ручное подтверждение (`manual ack`) только после успешной обработки или отправку в DLQ (Dead Letter Queue) при неустранимых ошибках.
4. **Идемпотентность потребителей:**
   - Каждое событие содержит обязательный `event_id` (UUID), по которому подписчик проверяет дедупликацию.

---

## Последствия

### Позитивные последствия:
- **Полная развязка сервисов во времени (Temporal Decoupling):** Сервис задач работает на максимальной скорости и не ждет отправки уведомлений.
- **Отказоустойчивость:** Если `bot-service` временно перезапускается, сообщения накапливаются в очереди RabbitMQ и будут обработаны после восстановления.
- **Масштабируемость:** Несколько реплик консьюмера могут параллельно разбирать одну очередь по паттерну Competing Consumers.

### Негативные последствия и компромиссы:
- **Согласованность в конечном счете (Eventual Consistency):** Уведомление доставляется с задержкой в 50–200 мс после создания задачи.
- **Необходимость администрирования брокера:** Необходим мониторинг очередей, настройка политик DLQ и защита от переполнения диска.
