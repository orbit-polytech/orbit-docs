# ADR-004: Проверка JWT на Gateway и доверенная передача через gRPC-метаданные

## Статус
**Принято (Accepted)** — Октябрь 2026 г.

---

## Контекст
В микросервисной архитектуре существует два крайних подхода к аутентификации:
1. **Каждый сервис проверяет JWT самостоятельно:** Каждый микросервис должен знать публичный ключ, проверять подпись, обращаться к блэклисту и парсить клеймы. Это дублирует код, увеличивает нагрузку на CPU и требует синхронизации ключей во всех 8 микросервисах.
2. **Передача `user_id` клиентом в теле запроса (Request Body):** Клиент явно передает `{"owner_id": "123"}`. Это создает критическую уязвимость BOLA (Broken Object Level Authorization), когда любой злоумышленник может подставить чужой идентификатор.

---

## Решение
Принята схема **Edge Authentication & Trusted Context Propagation (Проверка на периметре с доверенной трансляцией контекста)**:

1. **Единая точка валидации:**
   - Внешний клиент (Flutter, Telegram-бот) отправляет HTTP-запрос со стандартным заголовком `Authorization: Bearer <JWT>` на `gateway-service`.
   - `gateway-service` валидирует цифровую подпись Ed25519 по публичному ключу, проверяет `exp` и сверяет `jti` с блэклистом в Redis.
2. **Очистка и трансляция идентификатора:**
   - Шлюз принудительно удаляет любые входящие заголовки `x-user-id` от клиента.
   - Шлюз извлекает `sub` (UUID актора) и добавляет доверенный заголовок в метаданные исходящего gRPC-вызова:
     `x-user-id: <uuid>`
3. **Граница доверия:**
   - Внутренние микросервисы (`tasks-service`, `schedule-service`) доступны **только внутри закрытой сети Docker `orbit-net`** и не имеют публичных портов.
   - Внутренний перехватчик `AuthInterceptor` считывает `x-user-id`, проверяет базовую длину и отсутствие спецсимволов и помещает типизированный `domain.OwnerID` в контекст запроса.
4. **Исключения для Healthcheck:**
   - Запросы к `/grpc.health.v1.Health/Check` пропускаются без проверки метаданных.

---

## Последствия

### Позитивные последствия:
- **Защита от подделки личности (Zero Spoofing):** Клиент физически не может передать фальшивый `x-user-id`, так как шлюз всегда перезаписывает его проверенным значением.
- **Производительность:** Внутренние микросервисы не тратят ресурсы на криптографическую валидацию токенов.
- **Чистота контрактов:** Из тел Protobuf-сообщений (`CreateTaskRequest`, `ListTasksRequest`) убраны поля `owner_id`. Идентификатор владельца берется из контекста вызова.

### Негативные последствия и компромиссы:
- **Требование жесткой сетевой изоляции:** Если разработчик по ошибке откроет порт `50051:50051` во внешний интернет в `docker-compose.yml`, злоумышленник сможет отправить прямой gRPC-запрос с любым `x-user-id`. Архитектура требует строгого соблюдения сетевого периметра.
