# Урок 2: Оптимистичная блокировка и границы агрегата

## 1. Как было сделано изначально (Антипаттерн инкремента версии в домене)

В первоначальной реализации оптимистичной блокировки методы доменного агрегата `Task` сами увеличивали номер версии:

```go
// ПЛОХО: инкремент версии внутри бизнес-методов
func (t *Task) Complete() error {
    t.status = TaskStatusCompleted
    t.version++ // <- Ошибка в дизайне!
    return nil
}

func (t *Task) Reschedule(newDeadline Deadline) error {
    t.deadline = newDeadline
    t.version++ // <- Ошибка в дизайне!
    return nil
}
```

А репозиторий при сохранении строго требовал:
`UPDATE tasks SET version = version + 1 WHERE id = $1 AND version = $2`
где в качестве `$2` ожидалась версия `task.version - 1`.

---

## 2. В чём скрытый баг

Представим реальный бизнес-сценарий: студент переносит дедлайн и одновременно завершает задачу:

```go
task.Reschedule(newDeadline) // version: 1 -> 2
task.Complete()              // version: 2 -> 3
repo.Save(ctx, task)         // ПАДЕНИЕ: репозиторий проверяет existing.Version() == task.Version() - 1 (2 != 3 - 1)
```

Репозиторий возвращал ложный `ErrVersionConflict`! Никакой параллельной гонки на самом деле не было — сущность была изменена дважды в рамках одного потока выполнения.

Более того, доменная сущность вообще не должна знать, как именно база данных обеспечивает параллельную консистентность.

---

## 3. Как правильно делать в реальном сервисе

1. **Домен хранит только исходную версию**:
   Сущность хранит поле `version int64`, полученное при загрузке из БД. Доменные методы меняют состояние, но **не трогают версию**.
2. **Версию проверяет и инкрементирует репозиторий при сохранении**:
   При сохранении репозиторий выполняет атомарный SQL-запрос:
   ```sql
   UPDATE tasks 
   SET title = $1, status = $2, version = version + 1 
   WHERE id = $3 AND version = $4;
   ```
   Если количество обновлённых строк `rowsAffected == 0`, это значит, что другой параллельный запрос успел изменить задачу раньше. В этом случае репозиторий возвращает чистый `domain.ErrVersionConflict`.
3. **Метод `task.IncrementVersion()`**:
   Вызывается адаптером репозитория только после успешного завершения транзакции в базе данных.
