# Урок 1: Атомарная идемпотентность и гонки (AIP-155)

## 1. Как было сделано изначально (Антипаттерн Check-Then-Act)

В первой версии `CreateTaskUseCase` логика идемпотентности выглядела наивно:

```go
// ПЛОХО: Неатомарная проверка
if input.IdempotencyKey != "" {
    existingID, found := uc.idempStore.Get(ctx, input.IdempotencyKey)
    if found {
        return uc.finder.FindByID(ctx, existingID)
    }
}

// Создаем задачу
task := domain.NewTask(...)
uc.saver.Save(ctx, task)
uc.idempStore.Set(ctx, input.IdempotencyKey, task.ID())
return task, nil
```

---

## 2. В чём скрытый баг

Если студент нервничает из-за медленного интернета и нажимает кнопку «Создать задачу» 5 раз подряд за полсекунды (или мобильное приложение при сбое сети делает быстрый retry), на сервер параллельно приходят **5 горутин с одинаковым `Idempotency-Key`**:

1. Все 5 горутин одновременно вызывают `Get()`: ключа ещё нет в хранилище, и все 5 получают `found == false`.
2. Все 5 горутин создают 5 разных задач в базе данных с разными ID.
3. Все 5 горутин перезаписывают ключ в хранилище.

**Итог:** студент получает 5 дубликатов одной и той же задачи в списке. Идемпотентность не сработала.

---

## 3. Как правильно делать в реальном сервисе

По стандарту **Google AIP-155** операция резервации ключа должна быть **атомарной** и происходить ДО создания сущности:

1. **Атомарная резервация (`Reserve`)**:
   В Redis это команда `SET key "in_flight" NX EX 60` (установить, только если ключа ещё нет, с таймаутом). В PostgreSQL — вставка строки в таблицу с уникальным индексом.
2. **Проверка хэша тела запроса**:
   Вместе с ключом сохраняется SHA-256 хэш входных данных. Если клиент присылает тот же ключ, но с другим названием задачи — сервер обязан вернуть `ErrIdempotencyConflict` (`400 Bad Request`).
3. **Статус `in-flight`**:
   Если второй параллельный запрос приходит, пока первый ещё выполняется в базе, сервер возвращает `ErrIdempotencyInFlight` (`codes.Aborted` / `409 Conflict`), предлагая клиенту повторить попытку через секунду.
4. **Завершение (`Complete`)**:
   После успешной вставки в базу статус ключа переводится в `completed` с привязкой ID созданной задачи.

```go
// ЭТАЛОН: Атомарная двухфазная резервация
existingID, completed, err := uc.idempStore.Reserve(ctx, scopedKey, requestHash)
if err != nil {
    return nil, err
}
if completed {
    // Задача уже создана ранее — безопасно возвращаем её
    return uc.finder.FindByID(ctx, existingID)
}

// Защита: если транзакция упадет, освобождаем ключ
defer func() {
    if !success {
        _ = uc.idempStore.Release(context.Background(), scopedKey)
    }
}()
```
