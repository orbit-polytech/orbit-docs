## 1. Проверить проект и инструменты

Нужны Git, Flutter SDK с совместимым Dart и средства сборки выбранного target. Источник ограничений — актуальные `pubspec.yaml`, `pubspec.lock` и Android-конфигурация репозитория [mobile](https://github.com/orbit-polytech/mobile), а не произвольное «обновить всё до последнего». Сейчас в pubspec задан Dart `^3.13.7`; точную версию Flutter для команды согласуем и запишем в README. Dart отдельно от Flutter для этого не устанавливаем.

```bash
git clone https://github.com/orbit-polytech/mobile.git
cd mobile
flutter --version
flutter doctor -v
flutter pub get
flutter devices
```

Зависимости BLoC, GoRouter, Dio, Hive CE и secure storage уже объявлены в проекте. Не создаём новый Flutter-проект поверх существующего и не меняем зависимости без причины. `pubspec.lock` приложения сохраняем в Git.

Для Android установи Android Studio либо необходимые Android SDK tools: Platform-Tools (`adb`), Command-line Tools и SDK/Build-Tools, требуемые текущей Gradle-конфигурацией. Лицензии принимаются через `flutter doctor --android-licenses`. NDK/CMake ставим нужной проекту версии, если их требует сборка, а не все возможные версии заранее. IDE — VS Code или Android Studio на выбор; Java-расширения VS Code не являются обязательными и не запрещаются для других задач.

## 2. Физический Android по USB

Это удобный вариант, если эмулятор слишком требователен к компьютеру. Компьютер всё равно выполняет сборку приложения; телефон снимает необходимость виртуализации Android.

1. Включи режим разработчика на телефоне и отладку по USB.
2. Подключи кабель с передачей данных.
3. Подтверди доверие компьютеру на телефоне. Постоянное разрешение выдавай только своему доверенному компьютеру.
4. Проверь `adb devices` и `flutter devices`. Статус `unauthorized` означает, что нужно подтвердить запрос на телефоне; на Windows может потребоваться драйвер производителя.
5. Запусти из каталога `mobile`:

```bash
flutter run -d <device-id>
```

`<device-id>` заменяется значением из `flutter devices`. На поддерживаемом debug-target `r` выполняет hot reload, `R` — hot restart; изменения конфигурации запуска могут требовать полного перезапуска. Скорость зависит от устройства и проекта.

## 3. Android Emulator

Создай AVD в Device Manager. Для первой проверки подходит, например, Pixel с Android 14 / API 34. Архитектуру system image выбирай под компьютер; x86_64 не является универсальным требованием для ARM-машин. Объём RAM и графический режим подбирай по ресурсам компьютера.

```bash
flutter emulators
flutter emulators --launch <emulator-id>
flutter devices
flutter run -d <device-id>
```

Если AVD завис на восстановлении состояния — сначала попробуй Cold Boot. При проблемах графики переключи режим в настройках AVD. Не начинай с удаления данных эмулятора: Wipe Data стирает приложения и их данные. Специальные образы с размером страницы 16 KB не нужны для первоначального запуска; их совместимость проверяется отдельной задачей.

### Если на системном диске мало места

Перенос AVD необязателен. Закрой эмулятор, сохрани резервную копию существующих AVD и используй отдельный каталог, например `D:\Android\avd`. Для новых устройств можно задать `ANDROID_AVD_HOME`:

```powershell
New-Item -ItemType Directory -Force 'D:\Android\avd'
setx ANDROID_AVD_HOME 'D:\Android\avd'
```

Перезапусти терминал и Android Studio, затем проверь путь и запуск AVD. Изменение переменной не переносит уже созданные устройства автоматически; существующие конфигурации и пути переносятся отдельно. Junction не требуется как обязательный второй шаг. Не удаляй исходный каталог до проверки переноса.

## 4. Chrome и Windows Desktop — дополнительные варианты

Для вёрстки и проверки состояний без эмулятора:

```bash
flutter run -d chrome
```

В DevTools можно включить режим мобильного экрана. Он не воспроизводит все особенности Android/iOS. Hot reload и поддержка плагинов зависят от версии SDK и target; проверяем фактическую работу. Chrome использует браузерные CORS-ограничения и не заменяет Android-проверку сети, системных отступов и локального хранения.

Если Windows-target включён в проекте и установлен toolchain Visual Studio с компонентами Desktop development with C++, можно дополнительно запустить:

```bash
flutter run -d windows
```

Это необязательная платформа, не обход требований безопасности production. Не нужно устанавливать desktop toolchain только ради первого мобильного PR.

## 5. Поднять backend-стенд

Доступы к организации, `infra` и приватным GHCR-образам выдаю я. Авторизация Docker — по [инструкции GHCR](../quickstart/ghcr-access.md), запуск — по [актуальному quickstart](../quickstart/local-setup.md). Мобильному разработчику не нужно клонировать и собирать все Go-сервисы.

Из каталога `infra` проверь `task status`, Swagger и публичный маршрут расписания на компьютере:

```bash
curl "http://localhost:8080/api/v1/schedule/groups?query=261&limit=20"
```

В PowerShell при наличии alias используй `curl.exe`. Порт `8080` — пример для стандартной конфигурации; сверяй `GATEWAY_HOST_PORT`. Расписание может возвращать ожидание синхронизации или временную недоступность — значения объяснены в [API расписания](../gateway/schedule-api.md).

Не присылай PAT, `.env`, пароли или полный вывод с секретами в чат и PR. Для мобильной части не нужны приватные JWT-ключи, пароли БД и LLM API keys.

## 6. Адрес Gateway: компьютер, эмулятор и телефон

`localhost` внутри телефона или Android Emulator означает само устройство, а не компьютер с Docker.

| Запуск клиента | Пример адреса Gateway |
|---|---|
| Chrome/Windows на том же компьютере | `http://localhost:8080` |
| Стандартный Android Emulator | `http://10.0.2.2:8080` |
| Телефон по USB с настроенным adb reverse | `http://127.0.0.1:8080` |
| Телефон по локальной сети | `http://<LAN-IP-компьютера>:8080`, только после отдельной настройки доступа |

Для USB при стандартном порте:

```bash
adb -s <device-id> reverse tcp:8080 tcp:8080
adb -s <device-id> reverse --list
```

Для отмены проброса:

```bash
adb -s <device-id> reverse --remove tcp:8080
```

При другом порте меняем значения согласованно. После переподключения устройства проверяем проброс заново. По LAN нужны согласованные адрес привязки Gateway и правило firewall: не открывай все порты Docker и не публикуй базы данных наружу. Если Gateway привязан только к loopback, одного LAN-IP будет недостаточно.

### Конфигурация будущего сетевого слоя

В PR подключения API добавляем чтение `GATEWAY_BASE_URL` через `--dart-define`, документируем значение и проверяем его при запуске. Например, **после реализации чтения настройки**:

```bash
flutter run -d <emulator-device-id> --dart-define=GATEWAY_BASE_URL=http://10.0.2.2:8080
```

Для телефона с `adb reverse` используй `http://127.0.0.1:8080`. Сейчас стартовый Flutter-счётчик эту настройку ещё не использует. `--dart-define` подходит для публичного адреса сервера, но не для секретов: значения попадают в приложение.

Локальный HTTP может требовать ограниченной debug-настройки Android Network Security. Разрешение незашифрованного трафика не переносим без разбора в release; production использует HTTPS. В Chrome CORS при необходимости настраиваем на Gateway для согласованного dev-origin, а не отключаем безопасность браузера и не добавляем прокси к сайту расписания.
