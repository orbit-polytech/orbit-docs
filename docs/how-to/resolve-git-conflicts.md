# Что делать при конфликтах слияния в Git

В проекте Orbit AI принята политика **линейной истории коммитов**. Мы используем команду `git rebase` вместо создания промежуточных «грязных» коммитов слияния вида `Merge branch 'main' into feature/...`. 

Это руководство описывает стандартный алгоритм разрешения конфликтов при обновлении вашей рабочей ветки от актуального состояния `main`.

---

## 1. Почему возникает конфликт

Конфликт возникает, когда пока вы работали в ветке `feature/my-task`, в ветку `main` был влит Pull Request другого разработчика, изменивший **те же самые строки** в тех же файлах.

```text
       (main обновился) -> [Commit C] -> [Commit D] (origin/main)
      /
[Commit A]
      \
       (ваша ветка)    -> [Commit B1] -> [Commit B2] (feature/my-task)
```

При попытке сделать `rebase` Git последовательно «пересаживает» ваши коммиты `B1` и `B2` поверх свежего коммита `D`. Если изменения пересекаются, процесс приостанавливается для ручного выбора.

---

## 2. Пошаговый алгоритм разрешения конфликта

### Шаг 1. Сохранение незакоммиченных файлов

Перед началом убедитесь, что в рабочей директории нет несохраненных правок:

```bash
git status
# Если есть незавершённые правки, закоммитьте их или спрячьте в stash:
git stash
```

---

### Шаг 2. Обновление локальной ветки `main`

Подтяните свежие изменения из удаленного репозитория:

```bash
git checkout main
git pull origin main
```

---

### Шаг 3. Запуск Rebase

Переключитесь обратно в свою рабочую ветку и запустите процедуру перебазирования:

```bash
git checkout feature/my-task
git rebase main
```

Если возник конфликт, Git выведет сообщение:

```text
Auto-merging internal/transport/taskgrpc/handler.go
CONFLICT (content): Merge conflict in internal/transport/taskgrpc/handler.go
error: could not apply b1a2c3d... feat: add complete task handler
Resolve all conflicts manually, mark them as resolved with
"git add/rm <conflicted_files>", then run "git rebase --continue".
You can instead skip this commit: run "git rebase --skip".
To abort and get back to the state before "git rebase", run "git rebase --abort".
```

---

### Шаг 4. Разрешение конфликта в VS Code

Откройте конфликтующий файл в редакторе VS Code. Git пометит спорные блоки специальными маркерами:

```go
<<<<<<< HEAD (текущие изменения из ветки main)
	if req.GetLimit() > 100 {
		return nil, status.Error(codes.InvalidArgument, "максимальный лимит 100")
	}
=======
	if req.GetLimit() > 500 {
		return nil, status.Error(codes.InvalidArgument, "максимальный лимит 500")
	}
>>>>>>> feat: add complete task handler (ваши изменения)
```

1. Нажмите кнопку **«Resolve in Merge Editor»** в правом нижнем углу VS Code.
2. Вдумчиво выберите правильный вариант:
   - **Accept Incoming** (взять ваше новое изменение);
   - **Accept Current** (оставить изменение из main);
   - **Accept Both** или вручную объединить логику.
3. Удалите все разделительные маркеры `<<<<<<<`, `=======`, `>>>>>>>`.

---

### Шаг 5. Обязательная проверка компиляции и тестов

Сразу после ручной правки кода убедитесь, что проект компилируется и тесты проходят:

```bash
go test ./...
golangci-lint run ./...
```

---

### Шаг 6. Индексация и продолжение Rebase

Добавьте разрешенные файлы в индекс и продолжите процедуру:

```bash
# 1. Помечаем файл как разрешенный
git add internal/transport/taskgrpc/handler.go

# 2. Продолжаем перебазирование
git rebase --continue
```

Если у вас было несколько коммитов с конфликтами, Git может остановиться еще раз. Повторите шаги 4–6 для каждого шага, пока в консоли не появится:

```text
Successfully rebased and updated refs/heads/feature/my-task.
```

---

### Шаг 7. Спасательная кнопка: отмена в случае паники

Если вы запутались в конфликтах или случайно испортили код, в любой момент можно полностью прервать процедуру и вернуть ветку в исходное состояние:

```bash
git rebase --abort
```

---

### Шаг 8. Отправка ветки в GitHub (`--force-with-lease`)

Поскольку `rebase` переписал хэши ваших коммитов, обычный `git push` будет отклонен. Отправьте ветку с безопасным флагом `--force-with-lease`:

```bash
git push --force-with-lease origin feature/my-task
```

> [!IMPORTANT] Почему `--force-with-lease`, а не `--force`
> Флаг `--force-with-lease` проверяет, не отправил ли кто-то другой коммиты в вашу удаленную ветку, пока вы делали rebase. Если ветка изменилась кем-то еще, команда защитит чужую работу от случайного перезаписывания.

---

## 3. Сравнение: Как нельзя и Как правильно

<div class="grid" markdown>

<div class="card" markdown>
### :x: Как нельзя

- **Делать `git merge main` внутри своей фиче-ветки.** Это плодит бесконечные коммиты `Merge branch 'main' into ...` и превращает дерево коммитов в хаос.
- **Использовать грубый `git push --force`.** Вы можете случайно стереть чужие правки, сделанные тимлидом или коллегой.
- **Слепо выбирать «Accept Incoming», стирая код коллеги из main.** Всегда вчитывайтесь в контекст чужих правок, чтобы не сломать соседнюю функциональность.
- **Коммитить код с неразрешенными маркерами `<<<<<<< HEAD`.** Такой код не скомпилируется и сломает CI.
</div>

<div class="card" markdown>
### :white_check_mark: Как правильно

- **Использовать `git pull --rebase origin main`** для синхронизации с главной веткой.
- **Всегда запускать `go test ./...`** перед выполнением `git rebase --continue`.
- **Пушить перебазированную ветку строго через `git push --force-with-lease`.**
- **Использовать встроенный Merge Editor в VS Code** для наглядного трехпанельного сравнения.
</div>
