# Диагностика кэша и синхронизации расписания

Этот раздел относится к текущему Schedule с `contracts v0.5.0`, Redis-кэшем и Redis Streams. Все команды выполняются из `infra`. Не публикуйте `.env`, DSN, пароли и полный вывод конфигурации контейнеров.

## 1. Сначала определите состояние API

```bash
curl -i "http://localhost:8080/api/v1/schedule/groups/261-334"
task status
docker compose --profile apps logs --tail 100 schedule-migrate schedule-service gateway-service
```

| Результат | Что проверять |
|---|---|
| `200 READY` | `is_stale`, даты проверки, выбранный период и период публикации |
| `200 PENDING_SYNC` | Задание принято или уже существует; проверить воркеры и источник, затем повторить с задержкой |
| `404` | Название группы и обновление локального реестра |
| `503` | Доступность Schedule; если нет расписания — доступность очереди и включение синхронизации |
| `504` | RPC timeout и задержки сервиса/БД |

`READY` с пустым `days` не означает отсутствие группы. За пределами `published_from` / `published_to` нельзя делать вывод о каникулах. `UNSPECIFIED` не следует превращать в готовность или ожидание на клиенте. Полная семантика — [API расписания](../gateway/schedule-api.md).

Healthcheck Schedule не ждёт загрузки всех групп. Мигратор должен завершиться с `Exited (0)`. Runtime и `schedule-migrate` должны соответствовать одной версии схемы, включая миграцию поколения синхронизации.

## 2. Доступность Redis и кэш группы

Команды используют пароль внутри контейнера и не выводят его:

```bash
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli PING'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli TTL "schedule:cache:v1:group:261-334:regular"'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli PTTL "schedule:cache:v1:group:261-334:regular"'
```

Для текущего Compose используется Redis DB `0`. При другой базе добавьте соответствующий `-n` к `redis-cli`.

- `TTL > 0` — оставшееся время хранения, не возраст данных и не время до следующей синхронизации.
- `-2` — ключ отсутствует; запрос может успешно получить расписание из PostgreSQL.
- `-1` — ключ без срока истечения; для кэша Schedule это повод проверить путь записи.
- Начальный TTL — `24h` плюс положительный jitter `0..2h`. Он закономерно уменьшается.
- `KEEPTTL` сохраняет исходное время истечения при отметке устаревания, но не замораживает счётчик.
- Актуальность определяется отдельно через `SCHEDULE_FRESHNESS_TTL` и метаданные проверки.

Один ключ используется всеми посетителями группы и всеми диапазонами дат. `singleflight` защищает загрузку при промахе внутри одного процесса, не координирует все реплики.

## 3. Очереди: записи, pending и lag — разные показатели

```bash
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli XLEN sync:v1:stream:priority'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli XLEN sync:v1:stream:periodic'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli XINFO GROUPS sync:v1:stream:priority'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli XINFO GROUPS sync:v1:stream:periodic'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli XPENDING sync:v1:stream:priority schedule-sync-workers'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli XPENDING sync:v1:stream:periodic schedule-sync-workers'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli HLEN sync:v1:dedup'
docker compose exec redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli ZCARD sync:v1:delayed:zset'
```

Если Stream или consumer group ещё не создан, отсутствие ключа/`NOGROUP` само по себе не доказывает потерю данных: проверьте включение и запуск воркера.

| Показатель | Правильная интерпретация |
|---|---|
| `XLEN` | Число сохранённых записей, не число успешно обновлённых групп |
| `pending` / `XPENDING` | Полученные, но ещё не подтверждённые записи |
| `lag` | Не доставленные этой consumer group записи, когда Redis может вычислить значение |
| `HLEN sync:v1:dedup` | Число текущих маркеров дедупликации; оценивать вместе с очередями и повторами |
| `ZCARD sync:v1:delayed:zset` | Отложенные задания, ожидающие повторной попытки |

`XACK` снимает запись с pending, но не удаляет её из Stream. Даже нулевые pending и lag не доказывают успешную загрузку расписания: задание могло завершиться ошибкой либо перейти в отложенный повтор. Ненулевой dedup во время активной работы нормален, пустой dedup не доказывает отсутствие всех ошибок.

## 4. Зависшие задания и ошибки источника

- Воркеры обслуживают priority и periodic с целевым соотношением 3:1, без обещания строгого глобального порядка.
- Lease `sync:v1:lock:<title>` берётся на 30 секунд и продлевается владельцем. Освобождение и продление проверяют токен; при потере владения работа отменяется. Дополнительная проверка поколения в PostgreSQL защищает запись от старого воркера.
- Зависшие pending-задания восстанавливаются через `XAUTOCLAIM`; проверка выполняется отдельно от чтения новых записей. Поэтому единичный pending не означает вечное зависание.
- Ошибки вызывают ограниченные повторные попытки с задержками. Проверяйте отложенную очередь и логи, не создавайте поток ручных повторов.
- Общий token bucket ограничивает все обращения к источнику, включая реестр. При `SCHEDULE_SYNC_RPS=2` скорость пополнения — два токена в секунду, ёмкость — пять: короткий всплеск возможен.

Не удаляйте вручную lock/dedup и не делайте `FLUSHDB` для устранения задержки: это может нарушить координацию, а DB `0` также используется Auth с другими пространствами ключей.

## 5. Redis недоступен

Уже сохранённое расписание читается из PostgreSQL при сбое кэша. Неизвестной группе по-прежнему соответствует `404`; незагруженной известной группе нельзя обещать `PENDING_SYNC`, если задание не подтверждено.

При начальной недоступности Redis приложение повторяет подключение с задержкой; обработка очередей запускается после восстановления. Пока очередь/распределённый лимитер недоступны, нельзя обходить их прямыми запросами к источнику. Успешное чтение из PostgreSQL не доказывает работоспособность обновления.

Compose также ожидает начальную готовность Redis перед стартом Schedule; этот порядок запуска не заменяет обработку сбоев во время работы.

## 6. Как подтвердить успешную синхронизацию

1. Получите для выбранной группы `READY`, проверьте занятия и известный период публикации.
2. Сопоставьте `last_checked_at`, `last_updated_at`, `is_stale` с логами работы этой группы.
3. Если нужно подтвердить массовую загрузку, проверьте фактически сохранённое расписание и метаданные групп в PostgreSQL по актуальной схеме миграций, а не по `XLEN`.
4. При неизменившемся содержимом `last_updated_at` может не измениться после успешной проверки — ориентируйтесь также на `last_checked_at`.
5. Не обещайте задержку HTTP «меньше 2 мс» без измерений: Redis — только часть полного запроса через Gateway, gRPC и календарную обработку.

Новый E2E-прогон и проверка после сбоя нескольких реплик — отдельные проверки, их нельзя считать выполненными по одному выводу Redis.
