# Архитектурные границы и изоляция Python-стека

В этом разделе объясняются архитектурные компромиссы и причины изоляции Python в экосистеме Orbit AI.

---

## 1. Почему не писать бэкенд целиком на Python?

Частый вопрос: «Если мы уже используем Python для AI и бота, почему не написать на FastAPI все остальные сервисы?»

Решение использовать **Go** для основных сервисов и **Python** только для AI/бота принято на основе строгих инженерных критериев:

| Критерий | Go (бэкенд) | Python (ai & bot) |
|---|---|---|
| **Потребление памяти** | ~15–30 МБ на сервис в Docker | ~120–250 МБ на процесс |
| **Параллелизм** | Миллионы легких горутин без GIL | Асинхронный event loop (`asyncio`), чувствителен к блокирующему коду |
| **Строгая типизация** | Компилируемый язык, 0 шансов словить `AttributeError` в рантайме | Динамический язык с проверкой типами через MyPy |
| **Экосистема ML/AI** | Ограниченная библиотека | Мировой стандарт (PyTorch, GenAI SDK, pgvector, NumPy) |

**Вывод:**
Go даёт нам сверхбыстрые и надёжные микросервисы со строгой Чистой архитектурой, а Python даёт доступ к лучшим мировым библиотекам генеративного ИИ.

---

## 2. Изоляция взаимодействия

1. Сервисы на Go **никогда не обращаются напрямую к Gemini API**. Если сервису расписания или задач потребуется нейросетевая подсказка, он обращается по gRPC к `ai-service`.
2. Вся работа с векторным поиском и эмбеддингами инкапсулирована внутри `ai-service`. База данных PostgreSQL хранит векторные таблицы в изолированной схеме `ai`.
3. Для локальной разработки без доступа к Google Gemini API предусмотрен режим-заглушка `AI_PROVIDER=fake`, который возвращает детерминированные моковые ответы и векторы из нулей и единиц, позволяя команде полноценно тестировать весь микросервисный стек без VPN и платных API-ключей.
