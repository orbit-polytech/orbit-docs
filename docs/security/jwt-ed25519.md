# JWT и асимметричная подпись Ed25519

В этом разделе детально объясняется, как устроен механизм авторизации Orbit AI, почему мы выбрали асимметричную подпись **Ed25519 (EdDSA)** и как правильно валидировать JWT.

---

## 1. Сравнение симметричной (HS256) и асимметричной (Ed25519) подписи

В простых учебных проектах часто используют симметричную подпись `HS256`, где для подписи и проверки используется один общий секретный пароль (`JWT_SECRET`).

**Почему в микросервисах HS256 опасен:**
При симметричной подписи `auth-service` и `gateway-service` обязаны знать один и тот же секретный ключ. Если скомпрометирован Gateway, злоумышленник получает возможность не только читать чужие токены, но и **самостоятельно выпускать валидные токены администратора** от имени любого студента!

**Почему мы выбрали Ed25519 (`EdDSA`):**
1. **Асимметрия**: Приватный ключ (`jwt_ed25519`) хранится **исключительно в `auth-service`**. Ни один другой сервис или шлюз к нему доступа не имеет.
2. `gateway-service` получает только **публичный ключ** (`jwt_ed25519.pub`). Шлюз может быстро проверять подпись входящих запросов, но физически не способен подписать поддельный токен.
3. **Скорость и безопасность**: алгоритм Ed25519 работает значительно быстрее устаревшего RSA, использует 32-байтные компактные ключи и математически защищён от атак по побочным каналам.

## 2. Разделение Access и Refresh токенов

| Характеристика | Access Token | Refresh Token |
|---|---|---|
| **Формат** | JSON Web Token (JWT) с подписью Ed25519 | Криптографически случайная строка (32 байта, base64url) |
| **Срок действия** | **15 минут** (короткоживущий) | **30 дней** (скользящий) |
| **Где проверяется** | В `gateway-service` локально по открытому ключу (без похода в БД) | Только в `auth-service` по базе данных PostgreSQL |
| **Хранение на бэкенде**| Сервер не хранит выпущенные токены (stateless) | В БД хранится только `SHA-256(refresh_token)` |
| **Возможность отзыва** | Истекает сам через 15 минут | Можно мгновенно отозвать при выходе из аккаунта |

> [!NOTE]
> Refresh-токен **намеренно не является JWT**. Это случайная непрозрачная строка (Opaque Token). Её невозможно подделать, а в базе хранится только её криптографический хэш.

## 3. Структура Payload Access-токена

В текущей реализации (`auth-service/internal/infrastructure/security/token_signer.go`) в access-токен включаются следующие claims:

```json
{
  "iss": "orbit-auth",
  "aud": ["orbit-api"],
  "sub": "0192c6b1-9a72-7a8e-a204-c38d58f3b201",
  "iat": 1760000000,
  "exp": 1760000900,
  "auth_time": 1759999900
}
```

* `iss` (Issuer): издатель токена (`orbit-auth`).
* `aud` (Audience): целевой потребитель (`orbit-api`).
* `sub` (Subject): внутренний UUID аккаунта пользователя в системе.
* `iat` (Issued At): время выпуска токена (Unix timestamp).
* `exp` (Expires At): время истечения (15 минут от `iat` по умолчанию).
* `auth_time` *(опционально)*: Unix timestamp последнего реального подтверждения личности (OTP или OAuth); при обычном `refresh` не обновляется и используется для чувствительных операций вроде смены email и привязки OAuth-провайдера.

!!! note "Что НЕ входит в текущие токены"
    Поля `role`, `sid`, `jti`, а также заголовки `kid` и `typ: "at+jwt"` в текущие access-токены **не включаются** (библиотека формирует стандартный заголовок `{"alg": "EdDSA", "typ": "JWT"}`). Системные роли (`student`, `teacher`, `admin`) хранятся на стороне `users-service`, а не в JWT.

## 4. Безопасная проверка токена в Gateway (`middleware/auth.go`)

Актуальная проверка реализована в `gateway-service/internal/transport/http/middleware/auth.go` (`TokenValidator`):

```go
func (v *TokenValidator) ValidateToken(tokenStr string) (uuid.UUID, error) {
	if strings.TrimSpace(tokenStr) == "" {
		return uuid.Nil, errors.New("пустой токен")
	}

	parser := jwt.NewParser(
		jwt.WithValidMethods([]string{jwt.SigningMethodEdDSA.Alg()}),
		jwt.WithIssuer("orbit-auth"),
		jwt.WithAudience("orbit-api"),
		jwt.WithExpirationRequired(), // Защита от бессрочных токенов
	)

	var claims jwt.RegisteredClaims
	token, err := parser.ParseWithClaims(tokenStr, &claims, func(token *jwt.Token) (any, error) {
		if token.Method.Alg() != jwt.SigningMethodEdDSA.Alg() {
			return nil, fmt.Errorf("неожиданный метод подписи: %v", token.Header["alg"])
		}
		return v.publicKey, nil
	})
	if err != nil {
		return uuid.Nil, fmt.Errorf("ошибка валидации токена: %w", err)
	}

	if !token.Valid {
		return uuid.Nil, errors.New("токен недействителен")
	}

	if claims.Subject == "" {
		return uuid.Nil, errors.New("claim sub отсутствует")
	}

	accountID, err := uuid.Parse(claims.Subject)
	if err != nil {
		return uuid.Nil, fmt.Errorf("claim sub не является валидным UUID: %w", err)
	}

	return accountID, nil
}
```

После успешной валидации `middleware.Auth` (или `middleware.OptionalAuth` при наличии заголовка `Authorization`) записывает `accountID.String()` в `context.Context` (`WithUserID`), откуда обработчики передают его во внутренние сервисы через gRPC metadata `x-user-id` (или в `AccountId` для `users-service`). При ошибке выставляется заголовок `WWW-Authenticate: Bearer ...` и статус `401 UNAUTHENTICATED`.
