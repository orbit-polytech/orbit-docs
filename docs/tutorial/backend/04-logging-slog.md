# 04. Структурированное логирование (slog)

Логирование в микросервисах Orbit AI строится на стандартном пакете **`log/slog`**, встроенном в Go. Мы отказались от внешних сторонних библиотек (`logrus`, `zap`, `zerolog`) в пользу нативного решения без сторонних зависимостей.

---

## 1. Концепция структурированного логирования

Обычный вывод текста через `fmt.Println` или неструктурированные сообщения непригодны для микросервисной архитектуры: их невозможно фильтровать в системах централизованного сбора логов (Grafana Loki, OpenSearch, ELK).

В структурированном логировании каждая запись представляет собой пару «ключ-значение» с типизированными атрибутами:

```go
// Неструктурированный лог (плохо):
log.Printf("задача %s создана для пользователя %s за %v", id, ownerID, elapsed)

// Структурированный лог (хорошо):
logger.InfoContext(ctx, "учебная задача создана",
    slog.String("task_id", id.String()),
    slog.String("owner_id", ownerID.String()),
    slog.Duration("elapsed", elapsed),
)
```

---

## 2. Построение логгера в зависимости от окружения

В `cmd/tasks-service/main.go` формат и уровень логирования определяются конфигурацией `Config`:

```go
--8<-- "examples/tasks-service/cmd/tasks-service/main.go:build_logger"
```

### Разница между форматами:
1. **`TextHandler` (Окружение `development`)**:
   Выводит логи в удобочитаемом для человека текстовом виде в терминал разработчика:
   ```text
   time=2026-10-12T14:30:00.123Z level=INFO msg="запуск tasks-service" port=50051 env=development log_level=info
   ```
2. **`JSONHandler` (Окружение `production`)**:
   Сериализует каждую строку лога в строгий JSON для автоматического парсинга:
   ```json
   {"time":"2026-10-12T14:30:00.123Z","level":"INFO","msg":"запуск tasks-service","port":50051,"env":"production","log_level":"info"}
   ```

## 3. Градация уровней логирования

В проекте приняты строгие правила выбора уровня логирования:

| Уровень | Назначение | Пример события |
| :--- | :--- | :--- |
| `DEBUG` | Детальная диагностика внутренних шагов алгоритма | «найдено 12 записей в буфере событий» |
| `INFO` | Штатные этапы жизненного цикла системы | «сервис запущен», «миграции успешно применены» |
| `WARN` | Ошибки клиента, не угрожающие стабильности сервиса | «задача не найдена (404)», «невалидный дедлайн (400)» |
| `ERROR` | Внутренние непредвиденные сбои системы | «база данных недоступна», «перехвачена паника в хендлере» |

> [!IMPORTANT] Защита от спама в алертах
> Ошибки валидации входных данных клиента (код gRPC `InvalidArgument` или `NotFound`) **никогда не логируются с уровнем `ERROR`**. В противном случае боты и случайные невалидные запросы будут триггерить ложные ночные алерты дежурным инженерам.

---

## 4. Централизованный gRPC-интерцептор логирования

Логирование сетевых запросов не дублируется в каждом хендлере. Вместо этого в цепочку gRPC внедряется **`LoggingInterceptor`**:

```go
--8<-- "examples/tasks-service/internal/transport/taskgrpc/interceptors.go:logging_interceptor"
```

### Преимущества интерцептора:
- Автоматически засекает точное время обработки запроса (`time.Since(start)`).
- Проставляет уровень лога в зависимости от gRPC-кода возврата:
  - `OK` -> `INFO`
  - Любая ошибка клиента (`InvalidArgument`, `NotFound`, `Canceled`) -> `WARN`
  - Внутренняя ошибка сервера (`Internal`) -> `ERROR`
- Фиксирует полный путь вызываемого метода (`info.FullMethod`).

---

## 5. Безопасность данных в логах

При формировании логов запрещено утекать конфиденциальные данные:
- ❌ Пароли и хэши паролей.
- ❌ Значения секретных ключей и JWT-токенов.
- ❌ Персональные данные студентов (номера паспортов, телефоны).

Допустимо логировать: идентификаторы сущностей (`task_id`, `user_id`), статус-коды, длительность выполнения, имя метода.

---

## 6. Антипаттерны: как нельзя и как правильно

### ❌ Как нельзя:
```go
// ОШИБКА 1: fmt.Println в продакшн коде
fmt.Println("Error:", err)

// ОШИБКА 2: Конкатенация строк в сообщении
logger.Error("Ошибка с задачей: " + taskID + ", ошибка: " + err.Error())

// ОШИБКА 3: Логирование пароля
logger.Info("авторизация пользователя", slog.String("password", req.Password))
```

### ✅ Как правильно:
```go
// Структурированные типизированные атрибуты
logger.ErrorContext(ctx, "не удалось сохранить задачу",
    slog.String("task_id", taskID),
    slog.String("error", err.Error()),
)
```

---

## Резюме

1. Используем стандартный `log/slog` без внешних зависимостей.
2. В `development` пишем понятный текст, в `production` — JSON.
3. Сетевые вызовы логируются централизованно через gRPC-интерцептор.
4. Ошибки клиентов логируются как `WARN`, внутренние аварии сервиса — как `ERROR`.
