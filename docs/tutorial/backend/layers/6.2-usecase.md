# 6.2 Порты и сценарии (Usecase)

Слой **Use Case (Сценарии использования)** описывает пользовательские процессы системы: создание учебной задачи, получение списка, перенос дедлайна и закрытие задачи.

Слой Use Case не содержит кода баз данных, SQL-запросов или gRPC-хендлеров. Всё взаимодействие с внешним миром происходит строго через абстрактные интерфейсы — **порты**.

---

## 1. Принцип разделения интерфейсов (ISP) в `ports.go`

Вместо монолитного интерфейса `TaskRepository`, объединяющего десятки методов, порты разделены по принципу **Interface Segregation Principle (ISP)**:

```go
--8<-- "examples/tasks-service/internal/usecase/ports.go:usecase_ports"
```

### Преимущества узких интерфейсов:
- **Минимальные зависимости**: сценарий `GetTaskUseCase` требует только `TaskFinder` и не зависит от методов записи или паблишера событий.
- **Простота тестирования**: в unit-тестах создаются легковесные моки, реализующие только один-два метода вместо 10 методов репозитория.
- **Детерминированное время (`Clock`)**: передача интерфейса `Clock` позволяет в тестах фиксировать время с точностью до наносекунды и проверять поведение системы при смене дат.

## 2. Сценарий создания задачи (`CreateTaskUseCase`)

Сценарий координирует создание задачи, дедупликацию и публикацию событий:

```go
--8<-- "examples/tasks-service/internal/usecase/create_task.go:create_task_usecase"
```

### Ключевые шаги сценария:
1. **Изоляция ключа идемпотентности (Google AIP-155)**:
   Ключ идемпотентности изолируется идентификатором текущего пользователя: `actor.String() + ":" + input.IdempotencyKey`. Это предотвращает конфликт, если два разных студента отправят одинаковый строковый ключ (например, `client-req-1`).
2. **Дедупликация**:
   Если задача с данным ключом уже существует в `IdempotencyStore`, сценарий загружает её и возвращает клиенту без повторной записи в БД и без отправки дублирующего события.
3. **Создание Value Objects и сущности**:
   Валидация бизнес-инвариантов делегируется фабричным методам домена (`NewTitle`, `NewDeadline`, `NewTask`).
4. **Сохранение и публикация**:
   Задача сохраняется через порт `TaskSaver`, фиксируется ключ в `IdempotencyStore` и генерируется событие `TaskCreated`.

> [!WARNING] Архитектурный риск: двойная запись (Dual-Write)
> В текущей in-memory реализации вызов `saver.Save()` и последующий `events.PublishTaskCreated()` выполняются последовательно.
> В распределённой системе с реальной БД и RabbitMQ при сбое сети между этими вызовами запись попадёт в базу, но событие в очередь не уйдёт.
> В главе 8 мы устраним этот риск с помощью паттерна **Transactional Outbox**.

## 3. Защита от перебора идентификаторов (IDOR) в `loadOwned`

При проектировании API одной из критических уязвимостей является **IDOR (Insecure Direct Object Reference)** — ситуация, когда пользователь меняет ID в запросе и получает доступ к чужим данным.

Если вернуть ошибку `PermissionDenied` (403), злоумышленник узнает, что задача с таким ID реально существует в системе.

Для защиты в `get_task.go` реализован централизованный хелпер **`loadOwned`**:

```go
--8<-- "examples/tasks-service/internal/usecase/get_task.go:load_owned_helper"
```

> [!IMPORTANT] Принцип сокрытия существования ресурса
> Если задача принадлежит другому пользователю (`!task.IsOwnedBy(actor)`), хелпер возвращает **`domain.ErrTaskNotFound`**. Для злоумышленника чужая задача неотличима от несуществующей.

### Защита от невалидной пагинации в `ListTasksUseCase`:
В `ListTasksUseCase` исключены «тихие умолчания». Если клиент передал отрицательное смещение (`offset = -5`) или некорректный лимит (`limit = 0`), сценарий возвращает ошибку `ErrInvalidPagination`:

```go
if limit <= 0 || limit > 100 {
    return nil, 0, fmt.Errorf("%w: лимит %d должен быть в диапазоне [1, 100]", ErrInvalidPagination, limit)
}
if offset < 0 {
    return nil, 0, fmt.Errorf("%w: смещение %d не может быть отрицательным", ErrInvalidPagination, offset)
}
```

## 5. Антипаттерны: как нельзя и как правильно

### ❌ Как нельзя:
```go
// ОШИБКА 1: Протекание SQL транзакций в Use Case
func (uc *UseCase) Execute(ctx context.Context, tx pgx.Tx) error { // Привязка к конкретной СУБД!
    // ...
}

// ОШИБКА 2: Тихие дефолты вместо ошибки валидации
if limit <= 0 {
    limit = 20 // Маскирует ошибку на стороне вызывающего клиента
}

// ОШИБКА 3: Раскрытие чужой информации через ошибку Forbidden
if task.OwnerID() != actor {
    return ErrForbidden // Злоумышленник понял, что задача с таким ID существует!
}
```

### ✅ Как правильно:
```go
// Сценарий зависит только от портов-интерфейсов:
func (uc *UseCase) Execute(ctx context.Context, actor domain.OwnerID, id domain.TaskID) error {
    task, err := uc.finder.FindByID(ctx, id)
    if err != nil {
        return err
    }
    // Чужие задачи возвращают NotFound:
    if !task.IsOwnedBy(actor) {
        return domain.ErrTaskNotFound
    }
    return nil
}
```

## Резюме

1. Интерфейсы объявляются узкими (ISP) по месту использования в `ports.go`.
2. `CreateTaskUseCase` изолирует ключи идемпотентности по пользователю.
3. Хелпер `loadOwned` защищает систему от IDOR-уязвимостей.
4. Валидация пагинации строгая, без неявных дефолтов.
