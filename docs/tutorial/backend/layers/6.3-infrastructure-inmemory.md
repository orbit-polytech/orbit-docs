# 6.3 Инфраструктура и in-memory хранилище

В чистой архитектуре слой **Infrastructure (Инфраструктура)** содержит адаптеры, реализующие интерфейсы портов, определённые в слое Use Case.

В этой главе мы разбираем in-memory адаптеры `tasks-service`: потокобезопасное хранилище задач `TaskRepository`, хранилище ключей идемпотентности `IdempotencyStore` и генератор идентификаторов `UUIDGenerator`.

---

## 1. Потокобезопасный `TaskRepository`

Поскольку gRPC-сервер обрабатывает каждый входящий запрос в отдельной горутине, обращение к структурам данных в памяти обязано быть строго синхронизировано.

Для этого в `TaskRepository` используется `sync.RWMutex`:

```go
--8<-- "examples/tasks-service/internal/infrastructure/inmemory/task_repository.go:inmemory_repo"
```

### Архитектурные особенности репозитория:
1. **Проверка контекста (`ctx.Err()`)**:
   В начале каждого метода проверяется состояние контекста. Если клиент оборвал вызов до взятия блокировки, репозиторий не тратит процессорные ресурсы и не ожидает освобождения мьютекса.
2. **Оптимистичная блокировка (Optimistic Locking)**:
   При сохранении существующей задачи проверяется условие:
   ```go
   if existing.Version() != task.Version()-1 {
       return domain.ErrVersionConflict
   }
   ```
   Если две параллельные горутины попытаются обновить одну и ту же задачу, первая успешно запишет версию 2, а вторая получит конфликт версий `ErrVersionConflict` и вернёт клиенту gRPC-код `codes.Aborted`.

## 2. Глубокое клонирование сущностей (`cloneTask`)

Критическая ошибка начинающих инженеров при написании in-memory репозиториев — сохранение и возврат прямого указателя `*domain.Task`.

### В чём заключается опасность:
Если метод `FindByID` вернёт оригинальный указатель из мапы, вызывающий сценарий сможет мутировать поля сущности. При этом:
1. Изменения применятся в памяти репозитория даже в том случае, если вызов `Save()` не произошёл (нарушение транзакционности).
2. Параллельное чтение задачи другой горутиной приведёт к гонке данных (Data Race).

### Решение:
Функция `cloneTask` восстанавливает полностью независимую копию объекта через доменный конструктор `ReconstituteTask`:

```go
func cloneTask(t *domain.Task) *domain.Task {
    return domain.ReconstituteTask(
        t.ID(),
        t.OwnerID(),
        t.Title(),
        t.Description(),
        t.Deadline(),
        t.Priority(),
        t.Status(),
        t.Version(),
        t.CreatedAt(),
    )
}
```

## 3. Детерминированная пагинация со вторичным ключом

При пагинации в памяти недостаточно сортировать записи только по времени `CreatedAt`:
Если несколько задач созданы в одну и ту же миллисекунду, функция `sort.Slice` может возвращать элементы в произвольном порядке при повторных вызовах. Это приводит к тому, что клиент при перелистывании страниц (`limit/offset`) будет видеть дубликаты одних задач и пропускать другие.

В `tasks-service` используется **сортировка со вторичным ключом**:
```go
sort.Slice(matched, func(i, j int) bool {
    if matched[i].CreatedAt().Equal(matched[j].CreatedAt()) {
        return matched[i].ID().String() < matched[j].ID().String()
    }
    return matched[i].CreatedAt().Before(matched[j].CreatedAt())
})
```
Если даты создания совпадают, порядок детерминированно фиксируется по лексикографическому сравнению `TaskID`.

## 4. Хранилище идемпотентности с контролем ёмкости (`IdempotencyStore`)

Для предотвращения утечки памяти (Unbounded Memory Growth) размер in-memory кэша ключей ограничен лимитом в 10 000 записей:

```go
--8<-- "examples/tasks-service/internal/infrastructure/inmemory/idempotency_store.go:idempotency_store"
```

> [!NOTE] Роль в продакшене
> В промышленной эксплуатации in-memory хранилище заменяется на распределённый Redis (команда `SET key task_id NX EX 86400` с TTL 24 часа), что подробно разбирается в главе 8.

## 5. Генерация идентификаторов без паник (`idgen`)

В стандартной библиотеке и сторонних пакетах часто встречается метод `uuid.Must(uuid.NewRandom())`, который вызывает `panic` при ошибке системного энтропийного генератора `/dev/urandom`.

В адаптере `internal/infrastructure/idgen/id_generator.go` генерация всегда возвращает явную ошибку `error`:

```go
--8<-- "examples/tasks-service/internal/infrastructure/idgen/id_generator.go:id_generator"
```

## 6. Антипаттерны: как нельзя и как правильно

### ❌ Как нельзя:
```go
// ОШИБКА 1: Обычная мапа без мьютекса
type UnsafeRepo struct {
    tasks map[string]*domain.Task // Мгновенный crash сервиса при concurrent map writes
}

// ОШИБКА 2: Возврат оригинального указателя
func (r *Repo) FindByID(id string) *domain.Task {
    return r.tasks[id] // Утечка внутреннего состояния!
}

// ОШИБКА 3: Паника при генерации ID
func NewID() string {
    return uuid.Must(uuid.NewRandom()).String() // Уронит сервис при нехватке энтропии ОС
}
```

### ✅ Как правильно:
```go
// Потокобезопасность через sync.RWMutex:
r.mu.RLock()
defer r.mu.RUnlock()

// Возврат глубокой копии:
return cloneTask(task), nil

// Явная обработка ошибок генератора:
id, err := uuid.NewRandom()
if err != nil {
    return domain.TaskID{}, fmt.Errorf("генерация UUID: %w", err)
}
```

---

## Резюме

1. Любой in-memory репозиторий обязан быть защищён `sync.RWMutex`.
2. Репозиторий изолирует указатели через глубокое клонирование `cloneTask`.
3. Оптимистичная блокировка `version` предотвращает потерю данных при параллельных изменениях.
4. Пагинация обязана иметь детерминированный вторичный ключ сортировки.
